# Открытые вопросы к команде разработки Paynet

Всё, что в документации помечено как **Draft / Черновик / Ciornă** или не описано. Ответы не додумываем: публикуем только подтверждённое, и для каждой операции добавляем проверенный пример интеграции.

| # | Тема | Приоритет | Что сейчас в документации |
|---|---|---|---|
| 1 | Статусы платежей, заказов и возвратов | Критический | «будет опубликовано позже»; новый заказ — `status` = `1` |
| 2 | Первоначальная привязка карты и получение `CardLinkHash` (оплата в один клик) | Критический | есть поле в заказе, в уведомлении и метод удаления; как карта привязывается — не описано |
| 3 | Возвраты: частичные и полные, ограничения, ошибки, сроки | Высокий | только поля запроса |
| 4 | Повторная отправка уведомлений: интервалы и таймауты | Высокий | «до 3 повторов» |
| 5 | Единообразие полей API и фактическое поведение сервера | Средний | описано по проверке на тестовом API 09.11 |

## 1. Статусы

1. Какие значения бывают у `status` в ответах `POST /api/order`, `GET /api/order/{id}`, `GET /api/order/merchant/{id}`, `GET /api/order/search` и что значит каждое?
2. Гипотеза из прошлых обсуждений (не подтверждена): 1 Registered, 2 Customer Verified, 3 Initialized to be Paid, 4 Paid, 5 Expired, 41 PartialCancel. Верна ли она и к какой модели относится: статус платежа в API, статус транзакции, значение в отчётах?
3. Факт с тестового API 09.11: заказ с истёкшим `expiryDate` возвращает `status` = `1`. Переходит ли заказ в «Expired» и когда?
4. Какой статус после полного и после частичного возврата?
5. Какие статусы конечные (больше не меняются)?

## 2. Привязка карты (One-click)

1. Как привязать карту при первой оплате: какой параметр передать в `POST /api/order` / форме checkout?
2. Где мерчант получает `CardLinkHash`: в уведомлении, в ответе `GET /api/order/...`, оба?
3. Нужно ли явное согласие покупателя на сохранение карты? Кто его собирает — Paynet на платёжной странице или мерчант?
4. Область действия токена: мерчант, `SaleAreaCode` или конкретный `Customer.Code`?
5. Срок действия `CardLinkHash`. Что происходит при перевыпуске или истечении карты?
6. Повторная оплата: нужен ли CVC, 3-D Secure, переход покупателя на страницу Paynet — или списание без участия покупателя?
7. Какие ошибки возвращаются при неверном или удалённом `CardLinkHash`?
8. Можно ли привязку протестировать в тестовой среде тестовой картой?

## 3. Возвраты

1. Сколько возвратов можно сделать по одному платежу? Можно ли несколько частичных?
2. Есть ли срок, после которого возврат невозможен?
3. Возврат синхронный (результат в ответе) или асинхронный? Есть ли уведомление о возврате?
4. Ошибки: сумма больше остатка, повторный полный возврат, возврат неоплаченного платежа — какие `code` и HTTP-статусы?
5. Возвраты для всех `MoneyType` (`CARD`, `APPLEPAY`, `GOOGLEPAY`, `MIA_QR`, `PAYNET`, `CASH_INVOICE`)?
6. Что возвращается при акции, когда `PaidAmount` < `Amount`: максимум `PaidAmount`?

## 4. Повторы уведомлений

1. Через какие интервалы идут до 3 повторов?
2. Сколько Paynet ждёт ответа сервера мерчанта (таймаут)?
3. Какие ответы считаются успехом: только `200` или любой `2xx`?
4. Есть ли ручная повторная отправка (из кабинета/поддержки) и с каких IP-адресов приходят уведомления?

## 5. Поля API и поведение сервера

1. Формат ошибки `errorInfo` (400 при неверном JSON / нет обязательных полей) — намеренно? Планируется ли единый формат?
2. Кодировка `PayerName` / `PayerSurname`: в боевом уведомлении 06.11 имя с диакритикой пришло как `Tom?a`. Ошибка кодировки? Может ли так же испортиться `Customer` (входит в подпись)?
3. Подпись MD5: планируется ли новая версия (например, HMAC-SHA256) с периодом совместимости?
4. Можно ли выделить отдельного тестового мерчанта для автоматических проверок документации на реальном API?

## Закрытые вопросы (ответы и проверки)

| Тема | Ответ |
|---|---|
| Боевой URL API | `https://ecom-api.paynet.md`, пути как в тесте |
| Тестовые карты отказа / 3DS | нет; тестируется только успешный платёж; при неуспехе — редирект на `LinkUrlCancel` |
| Уведомления | только `PAID`; при неуспехе уведомления нет; `FAIL` добавят позже |
| Секретные ключи | два разных: для формы checkout и для уведомлений |
| Заказ hosted checkout в API | виден в `GET /api/order/merchant/{Order}` |
| Протокол v0.5 | убран из документации |
| Повтор `Order` | те же данные → тот же платёж; другие данные или уже оплачен/в обработке → `500 TECHNICAL_ERROR`; в форме — страница «Plata a fost respinsă» |
| Часовой пояс `ExpiryDate` | время Кишинёва |
| Формат ошибок | `status` / `message` / `code` / `traceId` / `details`; `401` — с большой буквы (`Status`…); неверный JSON — `errorInfo` (проверено на тестовом API 09.11) |
| Регистр полей запроса | не важен: unlink принимает `CardLinkHash` и `cardLinkHash` (проверено 09.11); в документации везде PascalCase, как в примерах |
| Ключи уведомления | `Id` / `ExternalId` подтверждены боевым уведомлением 06.11; `ID` / `ExternalID` 06.11 отправлял симулятор портала v2 (ошибка, исправлена в v3) |
| Кодировка подписи | UTF-8 |
| Заголовки уведомления | только `Hash` и `Content-Type` |
| `MoneyType` в уведомлении | `CARD`, `APPLEPAY`, `GOOGLEPAY`, `MIA_QR`, `PAYNET`, `CASH_INVOICE`; при `APPLEPAY` / `GOOGLEPAY` данные карты тоже заполнены |
| Apple Pay / Google Pay в запросе | показываются при `MoneyType` = `Card` и `All` |
| `PaidAmount` | должен равняться `Amount`; отличается только при официально согласованной акции; мерчант получает `PaidAmount` − комиссия |
