# Ошибки и статусы

## HTTP-коды

| HTTP | `code` | Значение | Что делать |
|---|---|---|---|
| `200` | — | Успех. | — |
| `400` | `INVALID_PARAMETER` | Один или несколько параметров отсутствуют или неверны. `details` называет параметр. | Исправьте запрос. Не повторяйте без изменений. |
| `401` | `UNAUTHORIZED` | Bearer-токен отсутствует, неверен или истёк. | Снова вызовите `/auth` и повторите запрос один раз. |
| `404` | `NOT_FOUND_RECORD` | Нет платежа/записи с таким ID. | Проверьте ID (`paymentId` или ваш `Order`). |
| `500` | `TECHNICAL_ERROR` | Ошибка на стороне Paynet **или** повтор `Order`, который нельзя использовать снова (см. ниже). | Проверьте через `GET /api/order/merchant/{Order}`, существует ли заказ; если это настоящая техническая ошибка — повторите позже с паузой. |
| `401` | `AUTHENTICATION_FAILED` | `/auth` с неверным логином или паролем. | Проверьте учётные данные. |

## Тело ошибки

```json
{
  "status": 400,
  "message": "One or more entered parameters are incorrect.",
  "code": "INVALID_PARAMETER",
  "traceId": "9b9346f9-f83a-465d-ac8d-dc382c460c22",
  "details": "The invalid parameter is: XXXX"
}
```

| Поле | Описание |
|---|---|
| `status` | HTTP-статус. |
| `message` | Сообщение для человека. |
| `code` | Машиночитаемый код ошибки (таблица выше). |
| `traceId` | ID запроса. Передайте его в поддержку Paynet, когда сообщаете о проблеме. |
| `details` | Дополнительная информация, например неверный параметр. |

> **Примечание:** ответ `401` на отсутствующий, неверный или просроченный токен использует ключи с большой буквы (`Status`, `Message`, `Code`, `TraceId`), а `401` от `/auth` на неверный пароль — обычные (`status`, `message`…). Читайте поля ошибки без учёта регистра.

### Неверный JSON или нет обязательных полей

Если тело запроса нельзя прочитать (неверный JSON, неверные типы, нет обязательного поля), API отвечает `400` в другом формате — ошибка внутри `errorInfo`:

```json
{
  "errorInfo": {
    "title": "One or more validation errors occurred.",
    "status": 400,
    "ppResponseCodeEnum": "TECHNICAL_ERROR",
    "ppResponseCode": 1,
    "ppResponseCodeText": "TECHNICAL_ERROR",
    "errors": {
      "$": ["JSON deserialization for type '…DeleteLinkedCardRequest' was missing required properties including: 'cardLinkHash', 'saleAreaCode', 'customerCode'."]
    },
    "traceId": "00-7c209d88f31e3e5cd2f7bd88ae2f23c2-ad167338e418068c-00"
  }
}
```

`errors` перечисляет проблемные поля. Обрабатывайте оба формата ошибок: сначала проверьте наличие `errorInfo`, затем читайте `status` / `code` / `message`.

Названия полей в запросе не чувствительны к регистру: принимаются и `CardLinkHash`, и `cardLinkHash` (проверено на тестовом API). Используйте написание из примеров.

## Повтор номера заказа (Order)

| Ситуация | Результат |
|---|---|
| Новый `Order` | Создаётся новый платёж. |
| Тот же `Order`, **те же данные**, платёж ещё не оплачен | Возвращаются тот же `paymentId` и `paymentLink`. Повтор безопасен, например после таймаута. |
| Тот же `Order`, **другие данные** (сумма, товары, …) | Server-to-server: HTTP `500`, `TECHNICAL_ERROR`. |
| Тот же `Order`, платёж уже оплачен или в обработке у банка-эмитента | Server-to-server: HTTP `500`, `TECHNICAL_ERROR`. Hosted checkout: покупатель видит страницу Paynet «Plata a fost respinsă» (счёт уже оплачен или в обработке). |

Тело ошибки в этих случаях:

```json
{
  "status": 500,
  "message": "One or more errors occurred.",
  "code": "TECHNICAL_ERROR",
  "traceId": "11de6054-87ef-484d-a368-7cfae0b452ff",
  "details": "Please verify the transmitted data and try again, or contact support."
}
```

**Правило:** один заказ в магазине = один `Order`. Если покупатель изменил корзину, создайте новый заказ с новым `Order`.

## Статус платежа

Объект платежа (`POST /api/order`, `GET /api/order/{id}`, `GET /api/order/merchant/{id}`, `GET /api/order/search`) содержит числовой `status` и даты `registered`, `paidDate`, `expiryDate`.

У только что созданного заказа `status` = `1`, а `paidDate` = `null`.

| `status` | Значение | Что делать |
|---|---|---|
| `1` | Зарегистрирован: заказ создан, оплаты не было | Ждать оплаты. Если покупатель ушёл со страницы, его можно снова отправить по той же `paymentLink`. |
| `3` | В обработке: покупатель нажал «Оплатить», ждём ответа банка | Не создавать заказ заново и не отменять его. Проверить статус позже. |
| `4` | Оплачен | Выполнить заказ. |
| `5` | Отменён: банк отклонил оплату, отмена антифродом или полный возврат | Окончательный. Для новой попытки оплаты нужен заказ с новым `Order`. |
| `6` | Частичный возврат | Окончательный. |

```
1 ──► 3 ──► 4 ──► 5  (full refund / полный возврат / rambursare totală)
      │      └──► 6  (partial refund / частичный возврат / rambursare parțială)
      └──► 5  (declined, antifraud / отказ, антифрод / refuz, antifraudă)
```

- `5` и `6` — окончательные статусы, после них ничего не меняется. Значение `2` не используется.
- Отдельного статуса «истёк» нет: если `ExpiryDate` прошёл, а оплаты не было, заказ остаётся в статусе `1`, но оплатить его уже нельзя.
- Антифрод срабатывает до подтверждения оплаты. Если вы получили проверенное уведомление `PAID`, антифрод этот платёж уже не отменит; статус `5` у оплаченного заказа означает только полный возврат.
- Считайте платёж оплаченным, если получили проверенное уведомление `PAID` или `status` = `4`.

### Неуспешная оплата и повторная попытка

Неуспешная оплата не порождает уведомление: покупатель возвращается на `LinkUrlCancel`. Проверьте статус через `GET /api/order/merchant/{Order}`:

| `status` | Что произошло | Как дать покупателю оплатить ещё раз |
|---|---|---|
| `1` | Покупатель не оплачивал (например, закрыл страницу) | Отправьте его по той же `paymentLink`. |
| `3` | Оплата ещё обрабатывается | Подождите и проверьте статус снова. Не создавайте новый заказ. |
| `5` | Банк отклонил оплату | Заказ закрыт. Создайте новый заказ с **новым** `Order` и отправьте покупателя по новой `paymentLink`. |

## Даты и форматы

| Где | Формат | Пример |
|---|---|---|
| `ExpiryDate` в запросах | `YYYY-MM-DDTHH:mm:ss`, **местное время Кишинёва** | `2026-12-31T23:59:59` |
| Даты в ответах о платеже | `YYYY-MM-DD HH:mm:ss` | `2026-04-01 15:01:12` |
| `eventDate` в ответе на возврат | `DD.MM.YYYY HH:mm:ss` | `09.11.2026 18:17:54` |
| Даты в уведомлениях | `YYYY-MM-DDTHH:mm:ss`, местное время Кишинёва | `2026-11-09T12:00:00` |
| `from` / `to` в `/api/order/search` | дата-время ISO 8601 | `2026-03-09T06:40:05.010Z` |
| `dateStart` / `dateFinish` в выписках | дата | `2026-03-01` |
| Суммы | целое, минимальные единицы | `1201` = 12,01 MDL |
| Валюта | числовой ISO 4217 | `498` = MDL |

Местное время Кишинёва — часовой пояс `Europe/Chisinau`: UTC+2 зимой, UTC+3 летом. Если сервер работает в UTC, переводите время перед формированием `ExpiryDate`, иначе заказы будут истекать на 2–3 часа раньше задуманного.

## Возвраты

`POST /api/order/refund`:

```json
{
  "PaymentId": 296901,
  "SaleAreaCode": "onlidocumentation_md",
  "RefundType": "full",
  "Amount": 50000,
  "Currency": 498,
  "Reason": "Customer request"
}
```

| Правило | Значение |
|---|---|
| Что можно вернуть | Только оплаченный платёж (`status` = `4`). |
| Сколько раз | **Один** возврат на платёж: полный (`full`) или частичный (`partial`). Второй возврат по тому же платежу невозможен. |
| Сумма | `Amount` в минимальных единицах; максимум — `PaidAmount` платежа (при акции он меньше суммы заказа). |
| Срок | 180 дней после оплаты. |
| Способы оплаты | Все, кроме `CASH_INVOICE`. |
| Результат | Сразу в ответе `POST /api/order/refund`. Уведомление на callback о возврате не отправляется. |
| Статус после | `5` после полного, `6` после частичного. Оба окончательные. |
| Баланс мерчанта | Если на счёте мерчанта в Paynet нет денег, возврат не пройдёт. |

### Ответы на возврат (проверено на тестовой среде)

| Ситуация | Ответ |
|---|---|
| Возврат выполнен | `200`, тело ниже |
| Платёж не оплачен | `404 NOT_FOUND_RECORD` |
| Сумма больше оплаченной | `400 INVALID_PARAMETER`, `details`: «The invalid parameter is: RefundType». Поле в `details` указано неточно: причина в сумме |
| Повторный возврат по тому же платежу (например, полный после частичного) | `400 INVALID_PARAMETER`, `details`: «The invalid parameter is: RefundType» |

```json
{
  "paymentId": 328733,
  "saleAreaCode": "onlidocumentation_md",
  "customer": "464566161",
  "eventDate": "09.11.2026 18:17:54",
  "refundType": "full",
  "currency": 498,
  "amount": 400,
  "merchant": "265505",
  "cardMask": "411111******1111",
  "cardLinkHash": null,
  "moneyType": "CYBER_SOURCE"
}
```

- `eventDate` в ответе на возврат имеет формат `DD.MM.YYYY HH:mm:ss`.
- `moneyType` здесь — код процессинга (например, `CYBER_SOURCE`), а не значение из уведомления (`CARD`…).
- После возврата `paidDate` платежа остаётся заполненным.
